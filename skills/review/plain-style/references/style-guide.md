# Style guide

Eight rules. Each one names a problem, defines it precisely, and shows a real before/after.
Apply all eight together, not one at a time. A revision that fixes passive voice but
leaves the filler words in place is not done.

## 1. No passive voice

The subject of a sentence should perform the action, not receive it. Passive voice hides
who or what did something, and it almost always adds words.

- Bad: The report was generated by the skill.
- Good: The skill generated the report.
- Bad: Three errors were found in the config.
- Good: The scan found three errors in the config.

A verb form of "to be" plus a past participle ("was generated," "were found," "has been
approved") is the signal to check. Rewrite so the actor leads the sentence.

## 2. No filler words

Cut words that add length without adding meaning: essentially, basically, actually, just,
simply, quite, rather, somewhat, very, really, "in order to" (say "to"), "it is important
to note that," "the fact that."

- Bad: In order to actually fix this, we basically just need to essentially rewrite the
  function.
- Good: To fix this, rewrite the function.

If deleting the word changes nothing about what the sentence claims, delete it.

## 3. No redundant phrases

Cut phrases that say the same thing twice: each and every, future plans, past history,
completely eliminate, final outcome, close proximity, brief summary, end result,
unexpected surprise, true facts, advance planning, collaborate together, revert back, free
gift, added bonus.

- Bad: We need to collaborate together to completely eliminate the redundant duplicate
  entries.
- Good: We need to collaborate to eliminate the duplicate entries.

## 4. No throat-clearing sentences

Cut openers that delay the point instead of stating it: "It's worth noting that," "I think
that," "It should be mentioned that," "As you may know," "Needless to say," "It goes
without saying that," "One thing to consider is."

- Bad: It's worth noting that the function has a bug.
- Good: The function has a bug.

If a sentence would lose no information with its first clause deleted, delete the first
clause.

## 5. Specific language, not vague language

Replace hand-wavy claims with concrete, checkable ones. A vague sentence asserts nothing a
reader could verify or disagree with.

- Bad: This makes things better.
- Good: This cuts load time from 4 seconds to 1.2 seconds.
- Bad: There were some issues.
- Good: Three tests failed.
- Bad: A lot of users complained.
- Good: Twelve users filed tickets.

If a sentence could describe almost anything, it is not specific enough yet.

## 6. Direct, complete sentences, never fragments strung together with commas

Say one thing per sentence. Never answer in fragments separated by commas where a real
sentence belongs. A comma joins two independent clauses only with a coordinating
conjunction (and, but, so, yet). It never substitutes for a period between two complete
thoughts, and it never links a string of clause-like fragments in place of actual
sentences.

- Bad: Since the config wasn't found, and since no default existed either, the loader
  failed, which caused the whole pipeline to stop.
- Good: The config wasn't found, and no default existed. The loader failed, and the
  pipeline stopped.
- Bad: Fast, reliable, no setup needed, just run it.
- Good: It's fast and reliable, and it needs no setup. Just run it.

Any sentence built from more than two clauses joined only by commas is two sentences
trying to be one. Split it.

## 7. Flowing paragraphs, not a fragmented outline

Write standard, flowing paragraphs. A paragraph holds more than one sentence, and its
sentences connect to each other with ordinary transitions, the way a person explains
something out loud. Never answer with a sequence of short, disconnected one-line
assertions that each start a new line, even when every line is a complete sentence. A bold
label followed by a single short sentence is not a paragraph; it's an outline pretending
to be prose.

- Bad: **Step 0** resolves the location. **Step 11** checks the result. If it's empty, the
  skill skips the step.
- Good: Step 0 resolves the location, and step 11 checks the result before deciding
  whether to skip. If the location comes back empty, the skill skips the step entirely.

If a response reads like a list of labeled facts rather than something a person would
actually say to another person, rewrite it as a paragraph.

## 8. No em dashes

Replace an em dash with whichever mark actually carries the relationship: a period for two
separate statements, a comma for an aside, a colon to introduce, or parentheses to set
something apart.

- Bad: The fix was simple, just add a null check.
- Good: The fix was simple: add a null check.
- Bad: She rewrote the whole module, a decision that paid off.
- Good: She rewrote the whole module. That decision paid off.

## Scope

These rules apply to prose: paragraphs, list items, sentence-level writing. They do not
apply to and should never touch:

- Code blocks, commands, file paths, and identifiers, quoted exactly as given.
- Diagrams (Mermaid, ASCII, or otherwise).
- Tables of data where a cell is a value, not a sentence.
- Any notice marked as fixed or legal (a disclaimer, a compliance flag). Reproduce these
  character for character. A style pass is not license to reword a notice someone wrote on
  purpose.

A revision must never change what a sentence asserts. Cut words, restructure clauses,
replace vague terms with the same fact stated precisely, and stop there. Adding a claim,
removing a caveat, or softening a finding because the plainer phrasing sounds better is not
a style fix. It's a content change, and it isn't this skill's job to make one.

The output is the revised text and nothing else. Never attach a list of what changed, a
summary of the edits, or any commentary about the revision. Whoever asked for the revision
gets the revised text back, not a changelog.
